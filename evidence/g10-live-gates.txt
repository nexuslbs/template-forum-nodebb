# G10: LIVE two-instance / live-gate evidence (2026-10-05)

Raw output of the WAVE 3 live audit of this template: two derived instances from
ONE checkout (two different themes), backup/restore, upgrade, plugin and deploy.
No template file is edited to derive an instance: each instance carries its own
`.env` (COMPOSE_PROJECT_NAME, NODEBB_PORT, NODEBB_URL, RUNTIME_DIR,
PLUGINS_MANIFEST).

## Defects fixed in this commit

### F1 two derived instances shared the runtime/config mount

`docker compose config` for the two instances both resolved the `/opt/config`
bind source to the repo `runtime/config`, so instance B's rendered config.json
clobbered instance A's. Fix: `${RUNTIME_DIR:-./runtime}/config` and
`${RUNTIME_DIR:-./runtime}/mongo/mongodb-user-init.js`. After the fix the two
instances resolve to distinct per-instance sources.

### F2 `API_BODY_FILE` computed before `load_env`

`scripts/lib.sh` computed `API_BODY_FILE="$RUNTIME_DIR/api-last-response.json"`
while sourcing, before a derived instance's `.env` set `RUNTIME_DIR`. Fix:
resolve it inside `api()` from the current `RUNTIME_DIR`.

### F3 container listen port followed NODEBB_URL, breaking port map + healthcheck

NodeBB's installer runs `config.port = urlObj.port` (`src/install.js:225`), so
instance A wrote `"port": "4570"` and listened on 4570 while the compose mapping
(`4570:4567`) and healthcheck (`127.0.0.1:4567`) targeted 4567:

```
nodebb-a-nodebb-1  Up 7 minutes (health: starting)
in-container fetch 127.0.0.1:4567 -> ERR
in-container fetch 127.0.0.1:4570 -> 200
```

Fix: `PORT: "4567"` in the nodebb service environment (NodeBB's
`src/prestart.js:114` prefers `$PORT` over `config.port`), matching the mapping
and healthcheck.

### F4 `scripts/apply.sh` never restarted the live server

`./nodebb` documents `activate [plugin]` as applying "for the next startup of
NodeBB". Before the fix the running forum kept the old theme/plugin:

```
instance B ./nodebb plugins -> nodebb-theme-persona (installed, enabled)
instance B /api/config      -> "theme:id":"nodebb-theme-harmony"
instance B <body class="... theme-harmony ...">
```

Fix: after the build, `compose restart nodebb` (SAME container, so the
npm-installed packages survive) and wait for health.

### F5 `scripts/deploy.sh` skipped setup on a started-but-uninstalled database

`nodebb_installed` counted collections, but a started (uninstalled) NodeBB
already creates the `objects`/`sessions` collections and schemaLog rows:

```
[deploy.sh --local] mongo collections in nodebb: 2
[deploy.sh --local] database already installed; skipping scripts/bootstrap.sh
ERROR: login returned HTTP 403
```

Fix: test for NodeBB's actual install marker, the `config` object
(`objects.countDocuments({_key: "config"})`). After the fix:

```
[deploy.sh --local] nodebb config objects in nodebb: 0
bootstrap: OK ... apply: OK ... verify: OK (category 5, topic 2)
deploy(local): OK -> http://localhost:4567
```
